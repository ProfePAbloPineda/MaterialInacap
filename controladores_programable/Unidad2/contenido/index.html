1. Del control local al control distribuido

En las experiencias anteriores se programó un controlador lógico programable (PLC) para recibir entradas, ejecutar una lógica de control y modificar salidas. En un sistema básico, sensores y actuadores se conectan al mismo controlador y las decisiones se toman localmente.

Sin embargo, en una instalación real es común que varios equipos deban compartir información: una interfaz HMI necesita conocer el estado del proceso; otro PLC debe recibir una autorización de transferencia; un computador de supervisión requiere registrar alarmas y variables históricas. Una red industrial permite intercambiar esa información entre dispositivos con reglas conocidas.

Figura 1. La red complementa el control local; no sustituye el programa de control ni los sensores.

1.1 ¿Qué información viaja por la red?

Los mensajes pueden representar estados discretos (motor en marcha, sensor activo), valores numéricos (temperatura, nivel, consigna), órdenes (partida, parada) o diagnósticos (falla de comunicación, código de alarma).

Ejemplo: dos estaciones transportadoras. El PLC de la estación A detecta una pieza y solicita permiso a la estación B. El PLC B informa que está disponible; A autoriza la transferencia. Cada PLC conserva el control de su propia máquina, pero ambos coordinan su funcionamiento intercambiando datos.

1.2 Requisitos particulares del entorno industrial

Además de conectividad, una red industrial puede requerir disponibilidad (continuidad de operación), robustez ante interferencias y condiciones ambientales, latencia reducida (demora entre solicitud y respuesta), comportamiento temporal predecible y diagnóstico de fallas. No todos los sistemas industriales exigen el mismo tiempo de respuesta: supervisar una temperatura no presenta las mismas restricciones que coordinar movimiento sincronizado.

Distinción importante. Que un dispositivo utilice Ethernet no implica que cualquier protocolo aplicado sobre Ethernet sea adecuado para tareas críticas en tiempo real. Debe evaluarse el protocolo, su implementación, la arquitectura y los requisitos del proceso.

2.1 Medios de transmisión

Los medios guiados conducen la señal por un soporte físico: par trenzado, cable coaxial o fibra óptica. Los no guiados utilizan ondas electromagnéticas, como Wi-Fi o enlaces de radio. La elección depende de distancia, velocidad requerida, interferencias, movilidad, costo, disponibilidad y condiciones de instalación.

Par trenzadoEconómico y habitual en Ethernet industrial.Distancia, instalación y compatibilidad con el entorno electromagnético.
Fibra ópticaInmunidad a interferencia electromagnética y aislamiento eléctrico.Costo y cuidado de conectores/transceptores.
Radio / Wi-FiMovilidad y menos cableado.Interferencias, cobertura, seguridad y variación de latencia.

2.2 Topologías

Una topología describe cómo se conectan físicamente o cómo se organizan lógicamente los nodos. En estrella, los equipos se conectan a un switch central. En línea, los dispositivos se encadenan cuando sus interfaces y el protocolo lo permiten. En anillo existen caminos redundantes, pero se requieren mecanismos adecuados para evitar bucles y permitir recuperación. La topología lógica de comunicación puede diferir de la disposición física.

3. ¿Qué es un protocolo de comunicación?

Un protocolo es un conjunto de reglas que especifica cómo se estructuran, transmiten, reciben e interpretan los mensajes. Dos dispositivos pueden estar unidos por el mismo cable y aun así no entenderse si usan protocolos incompatibles, parámetros diferentes o una interpretación distinta de las direcciones de datos.

Analogía técnica. Ethernet permite transmitir tramas dentro de una red local; IP identifica interfaces y permite dirigir paquetes; TCP ofrece un transporte orientado a conexión; y Modbus TCP define las operaciones de lectura y escritura de datos industriales. Son funciones complementarias, no nombres intercambiables.

3.1 Modelo OSI: siete capas

El modelo de referencia OSI organiza conceptualmente las funciones de comunicación en siete niveles. Ayuda a localizar problemas: puede funcionar el enlace físico y fallar, por ejemplo, el direccionamiento o la aplicación. No es una lista de siete protocolos que deban instalarse.

CapaNombreQué resuelve / ejemplo
7AplicaciónServicios y datos que usan las aplicaciones; por ejemplo, Modbus TCP.
6PresentaciónRepresentación, codificación o transformación de datos.
5SesiónOrganización y gestión lógica de diálogos entre aplicaciones.
4TransporteComunicación extremo a extremo; TCP o UDP.
3RedDireccionamiento y encaminamiento; IP.
2EnlaceTramas y direcciones MAC en Ethernet.
1FísicaSeñales, conectores y medio físico.

El uso práctico de Internet se describe habitualmente mediante el modelo TCP/IP, de cuatro capas: acceso a la red, Internet, transporte y aplicación. Las funciones OSI de sesión y presentación se integran normalmente en la capa de aplicación de TCP/IP.

3.2 Encapsulación: un dato recorre varias capas

Cuando una HMI consulta un valor de un PLC mediante Modbus TCP, la aplicación construye una solicitud Modbus; TCP transporta los datos entre aplicaciones; IP los dirige hacia la interfaz de destino; Ethernet los envía por la red local. En recepción se procesan esas envolturas en sentido inverso. Este proceso se denomina encapsulación y desencapsulación.

Para clases posteriores. Una dirección MAC identifica una interfaz dentro de un enlace Ethernet; una IP permite direccionamiento en una red IP; un puerto TCP permite llegar a un servicio concreto. No cumplen la misma función.

Trabajaremos progresivamente con un PLC Delta SE, una HMI Delta DOP-107EG y un computador. En esta primera clase la meta es comprender y dibujar la arquitectura, no configurar todavía el protocolo industrial.

4.1 ¿Qué equipo hace qué?

El PLC ejecuta la lógica de control y gobierna el proceso; la HMI representa variables y permite interacción; el PC programa, diagnostica o supervisa; y el switch interconecta interfaces Ethernet en la red local. El switch no interpreta, por sí mismo, la lógica del PLC ni traduce protocolos industriales.

4.2 Antes de comunicar: preguntas de ingeniería

  1. ¿Qué dispositivos deben intercambiar datos?
  2. ¿Qué información necesita cada uno?
  3. ¿Con qué frecuencia y con qué tiempo máximo de respuesta?
  4. ¿Qué interfaces físicas y protocolos admiten?
  5. ¿Qué consecuencias tendría una pérdida de comunicación?
